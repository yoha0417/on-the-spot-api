## 🚀 今後の実装ステップ

### Step 2: ハートビートAPIの実装
滞在中のユーザーがアプリを開いている間、バックグラウンドで定期的に現在地を送信し、滞在ステータスを延長するためのAPIです。

- **エンドポイント:** `POST /api/heartbeat`
- **リクエストボディ:** `{ "lat": number, "lng": number, "placeId": string }`
- **処理フロー:**
  1. `visits` テーブルから、該当ユーザーの `status = 'active'` かつ `place_id = リクエストのplaceId` のレコードを取得。
  2. レコードがない場合は `404 Not Found`（または既にチェックアウト済みとして扱う）。
  3. （オプション）念のため現在地とスポットの距離を再計算し、50mを大きく超えている場合は強制チェックアウト処理へ回す。
  4. 問題なければ、対象レコードの `last_heartbeat_at` を `CURRENT_TIMESTAMP` で更新し、`200 OK` を返す。

### Step 3: 自動チェックアウトのバッチ処理 (Cron)
ユーザーがアプリを落としたまま離れた場合などに備え、一定時間ハートビートがないユーザーを自動で退出させる仕組みです。

- **機能:** Cloudflare Workers の `Scheduled` イベント (Cron Triggers) を使用。
- **実行頻度:** 5分〜10分に1回程度 (`wrangler.jsonc` で設定)
- **処理フロー:**
  1. `visits` テーブルから `status = 'active'` のレコードを取得。
  2. 現在時刻と `last_heartbeat_at` を比較し、一定時間（例: 30分）以上経過しているレコードを抽出。
  3. 抽出したレコードを対象に `UPDATE` を実行。
     - `status` を `'checked_out'` に変更。
     - `checked_out_at` に現在時刻（または最終ハートビート時刻）を記録。

### Step 4: 投稿・タイムラインAPI (遅延公開ロジック)
このアプリのコア体験である「その場での熱量」と「退出後の余韻（タイムカプセル）」を実現します。

#### 4-1. 投稿作成 (`POST /api/posts`)
- **リクエスト:** `{ "content": string, "placeId": string, "is_delayed_publish": boolean }`
- **処理:** `posts` テーブルにデータを保存。現在 `active` な `visit` レコードと紐付ける。
APIの設計において、ユーザーID（userId）をリクエストの「ボディ（JSONの中）」に含めるのは、セキュリティ上のアンチパターンとされています。もしボディに入れてしまうと、悪意のあるユーザーが {"userId": "他人のID", "content": "ヤバい投稿"} とリクエストを書き換えて送信するだけで、簡単になりすましができてしまうためです。

現状のフェーズでは、本格的なJWT認証の実装はミドルフェーズに回し、今は開発用に仮の current-user-id のようなものを使って進めている状態ですよね。

Honoを使う場合、こういったユーザー識別情報はボディではなく、リクエストヘッダー経由で渡し、サーバー側のコンテキスト（c）に持たせるのがベストプラクティスです。

#### 4-2. タイムライン取得 (`GET /api/posts?placeId=...`)
- **要件:** 
  プレイス内の投稿を時系列順（新しい順）で取得する。その際、「即時公開の投稿」「公開条件を満たした遅延公開の投稿（タイムカプセル）」「自分の投稿」が1つのタイムラインに混ざるように取得ロジックを組む。フロントエンドで自分の投稿の状態が分かるよう、レスポンスに専用のフラグを含める。

- **取得ロジック（以下のいずれかの条件を満たす投稿を取得）:**
  1. **自分の投稿:** 無条件で取得する（`user_id` がリクエストユーザーと一致）。
  2. **他人の即時公開投稿:** `is_delayed_publish = false` の投稿（チェックイン状況に関わらず常に表示）。
  3. **他人の遅延公開投稿:** `is_delayed_publish = true` の投稿で、紐づく `visits` レコードの `checked_out_at` が `NOT NULL` であり、かつそこから **30分以上経過している** 場合のみ取得。

- **レスポンス要件（フロントエンド用フラグ）:**
  - 返却する投稿の各要素に `isWaitingForUnlock` (boolean) フラグを付与して返すこと。
  - **`isWaitingForUnlock` が `true` になる条件:** 
    「自分の投稿」かつ「`is_delayed_publish = true`」かつ「まだチェックアウトしていない（`checked_out_at`がNULL）、またはチェックアウトから30分経過していない」状態。

- **フロントエンド（React Native）の表示要件:**
  - 取得した投稿一覧を表示する際、`isWaitingForUnlock === true` の投稿には「🔒 この投稿はあなたがチェックアウトしてから30分後に他の人から見えます。」という案内文言をUI上に表示すること。

# バックエンド実装要件 (Hono + Cloudflare D1)

## エンドポイント
`GET /api/places/nearby`

## リクエスト (Query Params)
- `lat` (number, 必須): ユーザーの現在地の緯度
- `lng` (number, 必須): ユーザーの現在地の経度
- `radius` (number, 任意): 検索半径（メートル）。デフォルトは `3000` (3km) とする。
※ `@hono/zod-validator` を使用してバリデーションを行ってください。

## 処理ロジック (ハッカソン向け安全設計)
Cloudflare D1環境での三角関数の互換性問題を避けるため、以下の2段階で絞り込みを行ってください。

1. **SQLでの大まかな絞り込み（バウンディングボックス）**
   - 1度（緯度・経度）を約111kmとして計算し、`radius` に基づいて緯度・経度の検索範囲（minLat, maxLat, minLng, maxLng）を算出する。
   - Drizzle ORMの `between` 等を使用し、`places` テーブルからこの四角形の範囲内にあるスポットを抽出する。

2. **TypeScriptでの正確な距離計算**
   - 取得したスポットリストに対し、TypeScript側でHaversine公式を用いて正確な距離（メートル）を計算する。
   - 指定された `radius` を超えるスポットを除外し、距離が近い順（昇順）にソートしてレスポンスとして返す。レスポンスには計算した `distance` も含めること。

# 目的
Hono + Cloudflare D1環境において、JWTを用いた簡易的なユーザー認証APIとミドルウェアを実装してください。

# 前提
- 使用パッケージ: Hono標準の `hono/jwt` を使用すること。
- パスワードのハッシュ化: Cloudflare Workers（Edge環境）で動くため、Node.jsネイティブの `bcrypt` は使用不可です。代わりにWeb Crypto API（`crypto.subtle.digest` でのSHA-256等）か、純粋なJSライブラリ（`bcryptjs` 等）を使用してください。（ハッカソンのMVPなので、簡易的なハッシュ化で構いません）
- JWTシークレット: 環境変数 `JWT_SECRET`（`c.env.JWT_SECRET`）を使用すること。

# 実装要件1: 認証用コントローラーの作成
新規ファイル `src/interface/controllers/authController.ts` を作成し、以下の2つのエンドポイントを実装してください。
※ `@hono/zod-validator` を使ってリクエストのバリデーションを行うこと。

1. **ユーザー登録 (`POST /register`)**
   - リクエスト: `{ "email": "...", "password": "...", "name": "..." }`
   - 処理: パスワードをハッシュ化し、`users` テーブルに保存。
   - レスポンス: 発行したJWTトークン (`token`) とユーザー情報を返す。

2. **ログイン (`POST /login`)**
   - リクエスト: `{ "email": "...", "password": "..." }`
   - 処理: DBからユーザーを検索し、パスワードのハッシュ値が一致するか検証。
   - レスポンス: 成功時にJWTトークン (`token`) を返す。

# 実装要件2: JWT認証ミドルウェアの作成
新規ファイル `src/middleware/authMiddleware.ts` を作成してください。

- クライアントから送られてくる `Authorization: Bearer <token>` ヘッダーを取得。
- `hono/jwt` の `verify` 関数を使ってトークンを検証。
- 検証に成功した場合、ペイロードから `userId` を取り出し、`c.set("userId", userId)` としてコンテキストに保存し、`next()` を呼び出す。
- トークンが無い、または不正な場合は `401 Unauthorized` を返す。
